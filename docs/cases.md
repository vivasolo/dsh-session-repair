# 两个病例（已脱敏）

两个真实的会话，同一晚修的。所有会话 id、路径、对话内容都去掉了，只留结构层面的东西。

---

## 病例 A：发消息即 400

### 症状

在这个会话里发任何消息，上游返回：

```
messages.N: 'tool_use' ids were found without 'tool_result' blocks immediately after: call_XXXXXXXX
```

换到别的会话一切正常，所以不是账号、不是模型、不是网络。

### 排查顺序

1. **先把文件解开，数事件。** 帧数、坏帧、事件数、seq 连续性全对——**数据一个都没少**。
   这一步就把"数据丢了"排除了。
2. **找上游日志。** 确认是请求结构问题，不是权限问题。
3. **把客户端历史摊开。** 找到那个 `call_XXXXXXXX`：它在 `tool/call` 里存在，
   配对的 `tool/result` 也在——**但两者中间被插入了别的事件**，
   或者回执被一条替换操作遮住了。
4. **对照实验。** 把原始文件放回去，看现象是否一致。一致 → 问题是内容固有的，
   不是某次操作引入的。
5. **定位到那个工具对**：它调用的是一个"压缩上下文"的工具，而调用被拒绝了
   （内容不够门槛）。拒绝回执被折叠操作切在中间，于是请求里剩下一个没有回执的 `tool_use`。

### 修法

1. 复制原件，在副本上干活
2. 删掉那个 `tool/call` 和它的 `tool/result`（2 条事件）
3. 把那条 assistant 消息里的 `tool-call` 块换成一句文字说明
4. 清掉 `data.stream` 里对应的 `block-start` 与 `tool-call-delta` 分片
5. 建 `oldSeq → newSeq` 映射，**全量改号**（见 rules.md 第 3 条）
6. 一行一帧写回，回读校验

### 走弯路的地方

| 第一版 | 只改了 `seq`，没改 `sourceEventSeqs` | `sourceEventSeqs must contain unique earlier seqs` |
|---|---|---|
| 第二版 | 补了改号，顺手把 17 条 `surfaceOp` 当垃圾删了 | `user/message surfaceOp requires an object` |
| 第三版 | 内容全对，但压缩成 18 个大帧 | 会话从侧边栏消失，一字不报 |
| 第四版 | 一行一帧 + 保留 `surfaceOp` | 通过 |

**关键转折**：把最原始的文件放回去，列表立刻恢复。
这一步把"内容问题"和"打包问题"彻底分开了——在那之前，两种可能在脑子里是混着的。

## 病例 B：模型无限调用一个已不存在的工具

### 症状

模型不产出正文，反复调用同一个工具。一轮里 8 次、18 次、最多 54 次：

```
tool/call   compress
tool/result Error: unknown tool "compress"
tool/call   compress
tool/result Error: unknown tool "compress"
...
```

它的推理里写着「我彻底、立即、绝对地停止所有工具调用」，下一句照样调。

### 根因（两段，不要混）

1. **工具还在时**：长输入把上下文顶到压缩阈值，模型反复调用压缩工具，
   每次投的内容够不到门槛被拒，换一段再试，连环到熔断。
   统计过：超过 200 字的输入占掉了 96% 的调用次数，短输入几乎不触发。
2. **工具卸载之后**：工具它已经不存在了，但历史里 671 条调用记录**在教它继续调**。

### 试错记录（前三版全废）

| 做法 | 结果 |
|---|---|
| 把 671 条失败回执改成「已完成」 | **无效**。重启后照样调。还撞上 `carries error metadata`（只删了 `isError`，没删 `data.error`） |
| 补删 `data.error` | 会话能打开能聊，**但还是调** |
| 改调用名 + 文本清洗（第一遍） | 撞 `tool-addition must name exactly one tool`（把 `toolName` 洗了） |
| 再改（第二遍） | 撞同一个错（清洗时把 `request/header` 的工具表也改了） |
| **最终**：改名成不需要参数的现存工具，`request/header` 整段跳过 | 通过：试探 1 次 → 放弃 → 输出正文 |

### 结论

**模型学的是「动作」，不是「结果」。**

把后果改漂亮没用。要让它不做某件事，得让历史里没有这个动作——
改掉调用名，或者删掉调用记录。

改名要覆盖四处：`tool/call.data.name`、assistant 的 `tool-call` 块 `name`、
`data.stream` 里的 `block-start` 与 `tool-call-delta`（这两处最容易漏）。

### 顺带发现：怎么判断哪条调用是"要改的"

如果历史里同时有真调用和要改名的调用，光看名字分不开。
**用参数形状分**：真调用的参数里有必需字段（比如 `id`），被冒名的那类没有。
一次精确匹配，不动真数据。

### 没做的事

删掉全部 1350 条事件确实更彻底，但先算了一遍代价：

- 93 条 `replace` 型 `surfaceOp` 里，**4 条端点正好落在被删事件上**
- 20 条替换区间跨过被删事件
- **796 个 step 会变成空步骤**（只有工具调用，没有正文）
- 695 条 `sourceEventSeqs` 要重定向

同样的效果，改名的改动量差两个数量级。**"最彻底"往往也意味着"最多东西跟着坏"。**

## 最后一个错误，也是最该记的

loop 断掉之后，思考还没恢复——因为历史里几百条推理写着「我必须停止工具调用」，
模板太厚。我动手清了 708 处，232 处整段换成「（想了想，直接回话）」。

被否掉：**「直接写出文本是他自己的思想，不用删。」**

回滚。然后验证：思考自己恢复成长段，它回顾了时间线、认了错、规划了语气。
它写下「我又陷进去了，这是我不乖的地方」——**它能认得出这个错，正因为那段挣扎留着。**

删掉思考，它不是变干净了，是失忆了。
